# 檢索方法比較實驗

> 目的不是找出分數最高的方法，而是了解每種方法在這份資料上**為什麼好、為什麼不好**。
> 每組設定與基本版 A 只差一個變因；原始輸出見 [retrieval-experiments-raw.md](retrieval-experiments-raw.md)。

## 重跑方式

```bash
pip install -r api/requirements-dev.txt          # 只有實驗需要 sentence-transformers、jieba
EMBED_BACKEND=st python scripts/compare_retrievers.py --out docs/retrieval-experiments-raw.md
```

- 評測集：`tests/retrieval_eval.jsonl`，16 題（原文詞彙 4、換句話說 4、跨段落 3、詞彙不一致 4、數字代號 1）。
- 語料：`data/principal/docs/` 共 25 個段落，平均 83 字元（最短 32、最長 157）。
- 指標以段落為單位（切塊展開成段落 id 後依序去重）：Hit@K 與報告 §4 的「命中」定義相同；Recall@K 看跨段落題是否兩段都找回；MRR 看第一個正確段落排多前面。
- 嵌入在本機以 sentence-transformers 載入 HuggingFace 權重（CPU）。Docker 內的 Ollama `bge-m3` 是同一模型的 GGUF 版本，分數可能有小數點後的差異。

| | 只用 BM25（jieba 斷詞） | 12/16 | 15/16 | 0.88 | 0.85 | <1 |
| | 加權合併（min-max，α=0.5） | 14/16 | 16/16 | 0.97 | 0.94 | 78 |
| | RRF＋jieba | 13/16 | 16/16 | 0.94 | 0.90 | 77 |
| | B＋重排序（bge-reranker-base，Top-10） | 13/16 | 16/16 | 1.00 | 0.90 | 397 |

每題延遲在 CPU 上量測，主要是問題嵌入的時間。16 題的差距常常只差 1–2 題，**不能當作統計上的優劣**，以下分析看的是「哪一題、為什麼」。

## 各方法的優缺點

### 向量檢索（版本 A）

- **好在哪**：吃得下換句話說與詞彙不一致。eval-10「請長假、找人代課」和原文「育嬰留職停薪、代理教師」沒有任何共同詞，向量仍把 S1-2-1 排第 1、S2-3-1 排第 3；BM25 則把 S1-2-1 排到第 5。
- **壞在哪**：分數擠在一起，第 1 名常常不穩。eval-16 第 1、2 名的餘弦只差 0.015（S4-1-1 0.579 vs S1-3-2 0.564）；只要問法偏向「為學生辦的措施」，就會被語意相近但無關的段落搶走。這也是我們不用 K=1 的原因。

### BM25（關鍵字比對）

- **好在哪**：對原文詞、班級代號、時間（805、903、16:10）很準，而且幾乎不花時間、不需要模型；問法與原文用字一致時，分數差距很明顯（改用原文詞彙後 S1-2-1 分數 24.7，第 2 名只有 8.1）。
- **壞在哪**：
  1. 詞彙不一致就完全沒訊號：eval-10 與 S2-3-1 的共同二元組是 0 個，BM25 排第 20。
  2. 字元二元組會產生**跨詞的假詞**：「老**師請**長假」切出「師請」，剛好對上 S1-3-2「導**師請**協助督導」，而且這個二元組很少見、IDF 很高，S1-3-2 因此變成第 1 名。
- **jieba 斷詞沒有比較好**：它能避免「師請」這種假詞，但在 eval-07 把 S3-2-1 排到第 3（查過各段對上的詞：S4-2-1 只對上「上課」，但它很短又出現兩次，BM25 的長度正規化讓它排第 1；S3-2-1 對上「中文」但段落較長，另外還有「的」「課」這種到處都有的單字詞）。而且多一個套件、詞典沒有校務用語。在只有 25 段的語料上，字元二元組已經夠用。

### 混合檢索（版本 B）

- **好在哪**：兩路互補，向量負責語意、BM25 負責關鍵詞。Hit@1 從 13 提高到 15、MRR 從 0.90 提高到 0.97。eval-16 靠 BM25 的「課外」把 S1-3-2 拉回第 1；eval-07 靠「中文」「上課」兩個二元組（S3-2-1 寫「中文的補充說明」「上課時跟不上」）把 S3-2-1 拉到第 1。
- **壞在哪**：RRF 是把兩路名次平均，**只要其中一路完全看不到某段，那段就會被拖下去**。eval-10 的 S2-3-1 在向量排第 3、BM25 排第 20，合併後掉出 Top-3，Recall@3 從 1.00 降到 0.97。這是 B 唯一比 A 差的題，剛好是「詞彙不一致」題型。
- **RRF vs 加權合併**：加權需要先把兩種分數正規化、再調 α，結果還略差（MRR 0.94）；RRF 只看名次、沒有要調的參數，所以 B 用 RRF。

### 重排序（cross-encoder）

- **好在哪**：Recall@3 回到 1.00（eval-10 的 S2-3-1 又回到 Top-3），因為 cross-encoder 會把問題和段落放在一起讀。
- **壞在哪**：Hit@1 反而從 15 掉到 13（eval-12 的 S3-2-2 從第 1 掉到第 3），每題延遲變成約 5 倍（397 ms vs 76 ms）。在 Docker 裡還得安裝 torch（映像多 1 GB 以上），會吃掉 10 分鐘的啟動預算。對 25 段的小語料不划算，所以只留在實驗裡。

### 嵌入模型

- bge-m3 的 Top-3 最穩定（Recall@3 1.00）。bge-small-zh 的 Hit@1 反而多 1 題、速度快 10 倍以上，但 eval-12（「額外講義」vs 原文「補充教材」）掉到第 4。多語 MiniLM 在每項指標都最差，它是以英文為主訓練的，中文語意比較弱。
- 最後選 bge-m3 的主要原因其實是**部署**：Ollama 官方有 bge-m3，驗收機可以地端跑，Docker 映像不用裝 torch；bge-small-zh 沒有官方 Ollama 版本。

### 切塊方式

- **段落（A、B 採用）**：文件本身已經用 `###` 切成語意完整、自帶 id 的段落，一塊對應一個 id，sources 不需要另外計算歸屬。
- **加上「文件 > 章節」前綴**：解決段落太短、缺上下文的問題。eval-04「學習扶助的成效要怎麼評估」，S4-3-1 本文只寫「評估方式／參加學生」，沒有「學習扶助」也沒有「成效」，這兩個詞只出現在文件標題與 `## S4-3 成效評估`。加上前綴後 S4-3-1 從第 3 升到第 2（與第 1 名的差距從 0.10 縮到 0.002）。代價是每段都多了重複的標題字：eval-16 變成「閱讀測驗」所在的 S3-2-2 排第 1，推測是每段都帶著長標題，短段落本身的訊號被稀釋（S1-3-2 只有 70 字左右，前綴就佔了三分之一以上）。
- **整個章節一塊**：塊變大，主題被稀釋。S1-3「學務處與總務處報告」同時包含新實驗室與晨讀，eval-16 的晨讀段落因此掉到第 8；一個章節又會展開成 2–3 個段落，K=3 時實際送進 context 的段落數變多，LLM 得讀更多無關內容。
- **滑動視窗**：會切斷段落邊界，一個視窗常常橫跨兩段，sources 需要決定「這塊算哪一段」。一開始依位置排序 covered_ids，Hit@1 只有 6/16，因為視窗開頭沾到的是上一段的尾巴。改成依各段在視窗內的字數佔比排序後，Hit@1 回到 14/16，但 Recall@3 仍只有 0.88。**在段落本來就很短的語料上，視窗只是多一個要處理的問題。**

## 結論：為什麼最後是 A 與 B

1. 這份語料很小（25 段）、段落自帶 id，最大的風險不是「找不到」，而是**第 1 名不穩**和**詞彙不一致**。
2. A 用向量處理詞彙不一致；B 加入 BM25 處理關鍵詞與代號，用 RRF 讓第 1 名更穩。代價是遇到「BM25 完全看不到」的段落時，召回會下降。
3. 重排序、章節切塊、滑動視窗在這份資料上都沒有帶來好處，反而增加延遲或歸屬的複雜度。如果文件變長（例如整本校務手冊），段落不再是天然單位，這個結論就要重新檢驗。
